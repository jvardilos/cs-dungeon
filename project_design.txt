OVERVIEW
A console text-adventure set in a dungeon of connected rooms. The player moves a
small ASCII character around a room drawn on screen, picks up items, solves a
puzzle to open a locked door, and wins by finding the McGuffin, [NAME OF MCGUFFIN],
and carrying it to [FINAL ROOM].

HOW TO PLAY
  w / a / s / d   move up / left / down / right
  [take / use]    [TODO: pick up and use an item]
  q               quit
Every turn the room is redrawn so you can see where you are.

DESIGN APPROACH
Rooms. Each room is a 56 x 28 character box split into a 3 x 3 grid of cells
(18 wide, 9 tall). The player always stands in one cell, which makes movement,
item placement and walls simple: a room is just a small grid, not free
pixel-by-pixel positions. A move that would leave the grid is refused (that edge
is where a door or exit will go).

Classes. I used classes to keep the code organised:
  - Room:   what is in the room, how to draw it, and (TODO) its exits and lock.
  - Player: the player's cell, sprite, and inventory.
  - Item:   abstract base class for things in a room (doors, keys, the McGuffin,
            [TODO: others]). It stores the cell the item sits in; each subclass
            decides what happens when the player uses it (see POLYMORPHISM below).
The game keeps all rooms in a vector<Room> and the player in one place; the room
the player is in is tracked by an index into that vector [TODO: confirm once built].

Functions. Main work is split into functions rather than one long main():
  - generateMap():  builds the list of rooms.
  - controls():     the game loop - read a key, move the player, redraw.
  - Room::printRoom(): draws the border, the player sprite, and (TODO) items.
  - Player::move(): moves one cell and reports whether the move was allowed.

WHAT I LEARNED / PROBLEMS SOLVED
  - A bug where the room stored a pointer to a player that had already been
    destroyed. I fixed it by having main() own the player and pass it in.
  - Moving the player by screen coordinates was error-prone, so I store the
    cell (0-2) instead and convert to a screen position only when drawing.
  - The same bug appeared again with items: a Door created as a local variable in
    generateMap() was destroyed when the function returned, but the room still held
    a pointer to it, so reading its coordinates gave garbage (found with
    AddressSanitizer). Objects stored by pointer must outlive the function that
    creates them. The fix is to allocate them on the heap and let the room own them
    with std::unique_ptr, which frees them automatically. [TODO: confirm once
    implemented.] This also means rooms can no longer be copied, so the game
    passes rooms by reference.

POLYMORPHISM (items)
This was not covered in class. I have used the same idea heavily at work in Go
(interfaces: one call, different behavior depending on the concrete type), so the
concept was familiar but the C++ details were not. Claude helped me with those:
  - A base class Item with `virtual void use(Player &) = 0;`. The "= 0" makes the
    function pure virtual: Item is abstract and cannot be created, and every
    subclass (Door, Key, ...) must supply its own use(). This is the closest thing
    to a Go interface method.
  - Subclasses are declared `struct Door : public Item` and mark overrides with
    `override`, so the compiler reports a mismatched signature instead of silently
    creating a new function. (Unlike Go, inheritance is declared explicitly.)
  - Shared data (the cell coordinates) lives once in Item, and a subclass passes
    its values up through the constructor's initializer list:
    `Door(int x, int y) : Item(x, y) {}`. Assigning in the constructor body does
    not work if the base has no default constructor.
  - Behavior that is the same for every item (getCoords, updateCoords) is a normal
    function in Item; only behavior that differs per type is virtual.
  - The base class has a virtual destructor, so deleting a Door through an Item
    pointer runs the right destructor.
  - Polymorphism needs pointers (a vector<Item *>), because storing an Item by value
    would slice off the subclass part. That brought in the lifetime problem
    described above, and the use of std::unique_ptr to own the items.
  - Class definitions go in the header, function bodies in a .cpp, and headers
    that include each other are broken with forward declarations (`class Player;`)
    - a pointer or reference only needs the name, but calling a member needs the
    full header included in the .cpp.

SCREEN REDRAW
Each turn the screen is cleared with an ANSI escape sequence before the room is
redrawn, so the UI stays in the same place. I chose this over a library such as
ncurses because it is a single line and the project does not need more.
